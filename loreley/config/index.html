    loreley.config¶

    Centralised configuration for the Loreley application, backed by pydantic-settings and environment variables.

    Settings¶

    • Settings: BaseSettings subclass that loads core application configuration.
    • Profiles: LORELEY_PROFILE selects an optional configuration preset that applies scaling-oriented defaults when the corresponding fields are not explicitly set via environment variables. Supported values:
      • "default": keep built-in defaults (no overrides).
      • "large-repo-1m-30k": recommended defaults for running ~30k iterations on ~1M LOC repositories (after ignore filtering). Required settings remain required.
    • Environment: app_name, environment, log_level, logs_base_dir. log_level controls the global Loguru log level used across long-running processes (including the scheduler, workers, and CLI entrypoints); logs_base_dir (via LOGS_BASE_DIR) optionally overrides the parent directory for the logs/ tree. When set, logs are written under <LOGS_BASE_DIR>/logs/...; when unset, they default to <cwd>/logs/.... See the scripts documentation under docs/script for concrete examples.
    • API auth: LORELEY_API_WRITE_TOKEN is required for UI API POST routes, and LORELEY_AGENT_API_TOKEN is required for all /api/v1/agent/* routes. Generate both values yourself as deployment secrets; Loreley does not issue them. Both are bearer tokens and are masked in safe config exports.
    • OpenAI-compatible API: OPENAI_API_KEY, OPENAI_BASE_URL, and OPENAI_API_SPEC configure the static API key, base URL, and API surface for code embeddings, trajectory summarization in global_openai mode, and Kilocode provider fallback. OPENAI_API_KEY is treated as a secret and should be managed outside the database. When unset, OPENAI_API_KEY/OPENAI_BASE_URL fall back to the OpenAI Python client's own environment variable defaults for global OpenAI SDK callers. OPENAI_API_SPEC accepts:
      • "responses" (default): use the unified responses API (client.responses.create) for text generation.
      • "chat_completions": use the classic Chat Completions API (client.chat.completions.create) while preserving the same high-level behaviour.
      • Dynamic API keys: OPENAI_DYNAMIC_API_KEY_PROVIDER optionally points to a user-provided zero-arg Python callable (module:attr or module.attr) that returns a non-empty API key string. When configured, Loreley uses this dynamic provider instead of the global static OPENAI_API_KEY for internal OpenAI SDK calls. OPENAI_DYNAMIC_API_KEY_TTL_SECONDS is required in this mode and declares how long each returned token remains valid. OPENAI_DYNAMIC_API_KEY_REFRESH_SKEW_SECONDS optionally overrides the pre-expiry refresh margin; when unset, Loreley uses min(60, max(1, ttl_seconds // 10)). Internal SDK callers share one process-local cached token that refreshes before expiry; if a refresh fails but the cached token is still valid, Loreley keeps using the cached token until expiry and logs a warning. Kilocode planning/coding subprocesses fetch a fresh one-shot token immediately before each subprocess launch and do not overwrite the shared cached token.
      • Usage tracking: LLM_USAGE_TRACKING_ENABLED controls whether Loreley records usage rows for internal OpenAI SDK calls and supported agent backends. It defaults to true. LLM_USAGE_PRICING_PATH points to a versioned local pricing JSON file, and LLM_USAGE_PRICING_JSON can provide the same pricing payload inline. Pricing is used when a provider or CLI reports tokens without a USD cost, except for Kilo: Loreley treats Kilo's session-tree token and dollar aggregates as authoritative, leaves missing or zero token-bearing Kilo cost unpriced, and never reconstructs Kilo spend locally. Loreley does not fetch prices at runtime.
    • Database: either a raw DATABASE_URL or individual DB_* fields (scheme, host, port, username, password, database name, pool options, echo flag). DB_AUTO_MIGRATE controls whether API/scheduler/worker startup may initialize an empty database or apply supported native migrations automatically. Set it to false when startup must fail until an operator runs uv run loreley db migrate. DB_MIGRATION_LOCK_TIMEOUT_SECONDS controls the Postgres advisory-lock wait used by the native migration path.
    • Metrics: metrics_retention_days controls how long metrics are retained.
    • Task queue: TASKS_REDIS_URL, TASKS_REDIS_HOST, TASKS_REDIS_PORT, TASKS_REDIS_DB, TASKS_REDIS_PASSWORD, TASKS_QUEUE_PREFETCH, TASKS_DELAY_QUEUE_PREFETCH, TASKS_WORKER_MAX_RETRIES, TASKS_WORKER_TIME_LIMIT_SECONDS, and EXPERIMENT_ID configure the Dramatiq Redis broker connection details, worker prefetch behavior, retry policy, and actor time limits used by loreley.tasks.broker, loreley.tasks.workers, and loreley.entrypoints. The broker namespace and the single worker queue name are derived from EXPERIMENT_ID (not configurable) so multiple experiments can share a Redis instance safely. EXPERIMENT_ID can be either a UUID or a short slug; slugs are mapped to stable UUIDs (uuid5) and yield a stable naming namespace. When TASKS_REDIS_URL is set and includes credentials, only a sanitised scheme://host:port/db form is logged, never the raw URL or password. TASKS_QUEUE_PREFETCH and TASKS_DELAY_QUEUE_PREFETCH tune Dramatiq prefetch depth before worker construction. TASKS_WORKER_TIME_LIMIT_SECONDS is interpreted in seconds and converted to Dramatiq's millisecond time_limit: values <= 0 disable the time limit (no hard cap on actor runtime), while positive values enforce a per-job wall-clock limit.
    • Scheduler: SCHEDULER_REPO_ROOT, SCHEDULER_POLL_INTERVAL_SECONDS, SCHEDULER_MAX_UNFINISHED_JOBS, SCHEDULER_MAX_TOTAL_JOBS, SCHEDULER_SCHEDULE_BATCH_SIZE, SCHEDULER_DISPATCH_BATCH_SIZE, SCHEDULER_INGEST_BATCH_SIZE, SCHEDULER_STALE_RUNNING_RECLAIM_BATCH_SIZE, and SCHEDULER_STALE_RUNNING_MAX_RECOVERY_ATTEMPTS drive loreley.scheduler.main. SCHEDULER_MAX_TOTAL_JOBS is required and is enforced against the total number of EvolutionJob rows in the database (not a per-process counter). SCHEDULER_STALE_RUNNING_RECLAIM_BATCH_SIZE controls how many stale or malformed RUNNING jobs the scheduler reclaims per tick; set it to 0 to disable automatic reclaim. SCHEDULER_STALE_RUNNING_MAX_RECOVERY_ATTEMPTS controls how many times a job can be auto-requeued before the scheduler marks it FAILED. CAMPAIGN_PROGRAM_CHANGE_POLICY controls how loreley.program.md changes are handled during a running scheduler: locked (default) or auto; approve is rejected until an approval workflow exists. The scheduler also enforces single-scheduler-per-experiment using a Postgres advisory lock at startup. Before entering the main loop, the scheduler requires startup approval for the experiment root commit: it prints the observed eligible repo-state file count (and filter knobs) and asks a y/n question. In non-interactive environments, set SCHEDULER_STARTUP_APPROVE=true or pass --yes to proceed; otherwise the scheduler refuses to start (fail fast).
    • Worker repository: WORKER_REPO_REMOTE_URL, WORKER_REPO_BRANCH, WORKER_REPO_WORKTREE, WORKER_REPO_WORKTREE_RANDOMIZE, WORKER_REPO_WORKTREE_RANDOM_SUFFIX_LEN, WORKER_REPO_GIT_BIN, WORKER_REPO_FETCH_DEPTH, WORKER_REPO_CLEAN_EXCLUDES, WORKER_REPO_ENABLE_LFS, and WORKER_REPO_JOB_BRANCH_TTL_HOURS configure the worker repository base clone (upstream remote and branch, local base path, optional randomised suffix for isolated base clones, git binary, shallow clone depth, clean exclusions, optional Git LFS support, and remote job branch retention). Job branch naming is derived from EXPERIMENT_ID (not configurable) so pruning never affects other experiments. The worker creates isolated per-job git worktrees under <WORKER_REPO_WORKTREE>-worktrees/ so concurrent jobs do not share a mutable working directory, used by loreley.core.worker.repository.WorkerRepository. When the scheduler points SCHEDULER_REPO_ROOT at the same base clone, both processes share the same cross-process repo lock for clone, fetch, worktree, and primary-objective branch mutation paths.
    • Worker planning: WORKER_PLANNING_* options configuring how the planning agent is invoked (binary path, optional profile, maximum attempts, timeout, extra environment variables), used by loreley.core.worker.planning.PlanningAgent. The planner returns a Markdown plan document; the worker treats the backend output as plain text and extracts a short summary on a best-effort basis. WORKER_PLANNING_BACKEND selects the backend (default: loreley.core.worker.agent.backends.kilocode_cli:kilocode_planning_backend).
    • Worker coding: WORKER_CODING_* options configuring how the coding agent is invoked (binary path, optional profile, maximum attempts, timeout, extra environment variables), used by loreley.core.worker.coding.CodingAgent. The coding agent returns a Markdown execution report; the worker treats the backend output as plain text and extracts a short summary on a best-effort basis. WORKER_CODING_BACKEND selects the backend (default: loreley.core.worker.agent.backends.kilocode_cli:kilocode_coding_backend).
    • Cursor backend: WORKER_CURSOR_MODEL selects the model passed to the Cursor Agent CLI (default "gpt-5.2-high"), used by loreley.core.worker.agent.backends.cursor_cli.cursor_planning_backend() and cursor_coding_backend() when wiring Cursor as a backend for planning or coding. WORKER_CURSOR_FORCE (default true) appends --force so the Cursor agent allows commands unless explicitly denied; set it to false to omit the flag.
    • Kilocode backend: WORKER_KILOCODE_BIN selects the Kilo binary (default "kilo"). WORKER_KILOCODE_AGENT maps to kilo run --agent, WORKER_KILOCODE_MODEL maps to --model, and WORKER_KILOCODE_PLANNING_MODEL / WORKER_KILOCODE_CODING_MODEL optionally override the model for each phase. WORKER_KILOCODE_VARIANT maps to --variant. WORKER_KILOCODE_MODE is retained as a backward-compatible alias for the agent selector. WORKER_KILOCODE_PURE=true maps to kilo run --pure; preflight fails if the installed CLI lacks that flag. WORKER_KILOCODE_STATE_ROOT creates a separate HOME, XDG data/config/cache, temporary directory, and Kilo usage DB directory for each job_id/run_token; calls without those identifiers fail closed. WORKER_KILOCODE_JSON_OUTPUT toggles kilo run --format json output (default false); Loreley defaults to plain text because Kilo's JSON mode emits raw event streams rather than a single final Markdown document. WORKER_KILOCODE_USAGE_DB_PATH optionally points Loreley at the Kilo SQLite database used to read token and Kilo catalog cost data for usage tracking; when unset, Loreley asks kilo db path first and falls back to ~/.local/share/kilo/kilo.db. Kilo usage tracking requires kilo run --title so Loreley can correlate Kilo sessions with worker jobs. Usage tracking checks the expected Kilo session schema, sums root and descendant session aggregates, and records an unavailable usage event instead of failing a completed worker run when the DB is missing or incompatible. Loreley always injects a non-interactive headless agent policy that disables interactive, question, plan-transition, and suggestion tools. These settings are used by loreley.core.worker.agent.backends.kilocode_cli.kilocode_planning_backend() and kilocode_coding_backend() when wiring Kilocode as a backend for planning or coding. When running Kilo with an OpenAI-compatible gateway, set WORKER_KILOCODE_OPENAI_API_KEY, WORKER_KILOCODE_OPENAI_BASE_URL, and/or WORKER_KILOCODE_OPENAI_MODEL to let Loreley generate isolated provider config for the spawned subprocess. WORKER_KILOCODE_PROVIDER_CONFIG_MODE controls how this is done: auto (default) and config use KILO_CONFIG_CONTENT with {env:LORELEY_KILO_OPENAI_API_KEY} / {env:LORELEY_KILO_OPENAI_BASE_URL} references; native keeps Kilo's built-in openai/* model catalog while overriding its API key and base URL; legacy_env preserves the older KILO_PROVIDER_TYPE / KILO_OPENAI_* injection for pinned Kilo versions; and none disables provider injection so Kilo's persisted auth/config is used while retaining the headless policy. WORKER_KILOCODE_OPENAI_API_KEY remains the highest-precedence API key source for Kilo; when it is unset and OPENAI_DYNAMIC_API_KEY_PROVIDER is configured, Loreley fetches a fresh one-shot dynamic token immediately before each Kilo subprocess launch. If neither of those worker-specific paths is configured, Loreley falls back to the global static OPENAI_* / LORELEY_LLM_* settings for API key, base URL, and API surface. Because Loreley injects the Kilo API key only at subprocess start, dynamic-token Kilo runs are only safe when the token TTL is typically longer than the real planning/coding runtime. To select the API surface used by Kilo, set WORKER_KILOCODE_OPENAI_API_SPEC to:
      • "chat_completions": configures the openai provider
      • "responses": configures the openai-responses provider
    • Worker evaluator: WORKER_EVALUATOR_PLUGIN, WORKER_EVALUATOR_VERSION, WORKER_EVALUATOR_PYTHON_PATHS, WORKER_EVALUATOR_TIMEOUT_SECONDS, and WORKER_EVALUATOR_MAX_METRICS configure the evaluation plugin entry point, optional evaluator identity version, additional Python paths, subprocess timeout, and the maximum number of metrics to keep, used by loreley.core.worker.evaluator.Evaluator. Campaign baseline keys use WORKER_EVALUATOR_VERSION when set, otherwise a best-effort package version or source fingerprint for WORKER_EVALUATOR_PLUGIN. Set WORKER_EVALUATOR_VERSION when evaluator semantics, benchmark data, or scoring logic change without changing the plugin source.
    • Evaluation artifacts: WORKER_EVALUATION_ARTIFACTS_ENABLED controls whether evaluator-declared artifacts are materialized. Artifact storage accepts only WORKER_EVALUATION_ARTIFACT_ALLOWED_MIME_TYPES and enforces WORKER_EVALUATION_ARTIFACT_MAX_BYTES. Agent feedback is limited by WORKER_EVALUATION_AGENT_FEEDBACK_MODE (disabled, manifest, summary, or path), WORKER_EVALUATION_AGENT_FEEDBACK_MAX_ARTIFACTS, WORKER_EVALUATION_AGENT_FEEDBACK_MAX_DIAGNOSTICS, and WORKER_EVALUATION_AGENT_FEEDBACK_MAX_CHARS. WORKER_EVALUATION_ARTIFACT_AGENT_PATH_MAX_BYTES and WORKER_EVALUATION_ARTIFACT_AGENT_PATH_MIME_TYPES bound which artifact URIs can be exposed in path-mode agent feedback.
    • Worker evolution commits: WORKER_EVOLUTION_COMMIT_AUTHOR and WORKER_EVOLUTION_COMMIT_EMAIL configure git identity. Commit messages are deterministic: Loreley reuses coding.report.summary, then plan.summary, then the job id. It makes no separate commit-summary model request. The full normalized message is used for git; bounded CommitCard.subject and change_summary projections remain 72 and 800 characters for hot-path storage.
    • Trajectory summaries: set WORKER_PLANNING_TRAJECTORY_SUMMARY_MODEL whenever WORKER_PLANNING_TRAJECTORY_MAX_CHUNKS is greater than zero. WORKER_PLANNING_TRAJECTORY_SUMMARY_PROVIDER_MODE=global_openai uses OPENAI_API_KEY, OPENAI_BASE_URL, and OPENAI_API_SPEC. custom uses WORKER_PLANNING_TRAJECTORY_SUMMARY_API_KEY, WORKER_PLANNING_TRAJECTORY_SUMMARY_BASE_URL, and WORKER_PLANNING_TRAJECTORY_SUMMARY_API_SPEC. For providers that expose a thinking toggle, set WORKER_PLANNING_TRAJECTORY_SUMMARY_THINKING=enabled or disabled; the default provider_default sends no provider-specific field. WORKER_PLANNING_TRAJECTORY_SUMMARY_REASONING_EFFORT=high|max sends reasoning_effort with Chat Completions or reasoning.effort with Responses; provider_default omits it. Explicit effort is rejected when thinking is disabled. WORKER_PLANNING_TRAJECTORY_SUMMARY_MAX_OUTPUT_TOKENS bounds reasoning plus final output, while WORKER_PLANNING_TRAJECTORY_SUMMARY_MAX_CHARS bounds the cached final summary. Worker preflight reports the resolved mode, API surface, model, thinking, and effort settings and fails before work starts if the route is incomplete. Set WORKER_PLANNING_TRAJECTORY_MAX_CHUNKS=0 to disable LLM trajectory summaries.
    • Worker evolution global goal: WORKER_EVOLUTION_GLOBAL_GOAL provides a single, plain-language evolution objective that is shared across all jobs. When a job row does not provide a per-job goal, this value is used as the Global objective in both the planning and coding prompts so that the worker consistently optimises towards a user-defined high-level target.
    • Worker job leases: WORKER_JOB_LEASE_TTL_SECONDS and WORKER_JOB_HEARTBEAT_INTERVAL_SECONDS control how the worker keeps ownership of a RUNNING job. The worker renews the lease in the background while planning, coding, and evaluation are running. The scheduler only reclaims a job after the lease expires or required lease fields are missing.
    • Map-Elites preprocessing: MAPELITES_PREPROCESS_* options controlling which repository code files are considered for feature extraction (limits on file size, allowed extensions/filenames, excluded path globs, whitespace handling, and comment stripping), used by loreley.core.map_elites.preprocess.CodePreprocessor and the repo-state embedding file enumerator.
    • Map-Elites chunking: MAPELITES_CHUNK_* options controlling how preprocessed files are split into chunks (target and minimum lines per chunk, overlap, maximum chunks per file, and boundary keywords used by the chunker), used by loreley.core.map_elites.chunk.CodeChunker.
    • Map-Elites repo-state embedding filters: MAPELITES_REPO_STATE_EMBEDDING_MAX_LINE_CHARS and MAPELITES_REPO_STATE_EMBEDDING_MAX_CHUNK_CHARS skip pathological preprocessed files before they are sent to the embedding API. These filters apply only to repo-state file embeddings, are counted separately from empty/provider failures, and are included in the embedding cache manifest fingerprint.
    • Map-Elites code embedding: MAPELITES_CODE_EMBEDDING_* options configuring the embedding model, output dimensions (MAPELITES_CODE_EMBEDDING_DIMENSIONS, configured via environment variables and expected to remain stable for a given database), batch size, retry count, and exponential backoff for embedding requests, used by loreley.core.map_elites.code_embedding.CodeEmbedder.
    • Map-Elites dimensionality reduction: MAPELITES_DIMENSION_REDUCTION_* options controlling how commit embeddings are normalised, the target feature dimensions, minimum sample count for fitting PCA, rolling history size, and refit cadence, used by loreley.core.map_elites.dimension_reduction.DimensionReducer. MAPELITES_DIMENSION_REDUCTION_SEED seeds PCA randomness (e.g. randomized SVD) for reproducible projections. When MAPELITES_DIMENSION_REDUCTION_MIN_FIT_SAMPLES is unset, Loreley derives it from MAPELITES_SEED_POPULATION_SIZE (min 2) so cold-start seed warmup can fit PCA before the archive is populated. In repo-state mode, the input embedding is the repo-state code vector.
    • Map-Elites feature normalization and archive: MAPELITES_FEATURE_TRUNCATION_K sets the symmetric clip radius applied to PCA outputs before they are linearly mapped into [0, 1]^d; MAPELITES_FEATURE_NORMALIZATION_WARMUP_SAMPLES controls the minimum history required before fitting/using PCA (never below MAPELITES_DIMENSION_REDUCTION_MIN_FIT_SAMPLES); and MAPELITES_FEATURE_CLIP toggles defensive clipping. MAPELITES_ARCHIVE_CELLS_PER_DIM configures the fixed behavior-grid resolution used by loreley.core.map_elites.manager.MapElitesManager.
    • Map-Elites objectives, islands, and sampling: MAPELITES_OBJECTIVES is an ordered JSON list of unique {"name", "direction"} entries. Every admitted evaluation must provide every objective with the configured direction; the first entry is only the primary operational projection for status, baselines, and the convenience branch. MAPELITES_PARETO_FRONT_MAX_SIZE bounds each behaviour cell, while MAPELITES_PARETO_EPSILON controls dominance/equivalence tolerance. MAPELITES_ISLANDS is an ordered JSON list of independent island IDs; IDs are non-empty, unique, and at most 64 characters, and the first is the CLI/API default. Normal scheduling waits until every configured island has completed cold-start, preventing early islands from consuming another island's fixed search budget. MAPELITES_MIGRATION_INTERVAL_JOBS controls the per-island donor cadence; set it to 0 to disable migration. MAPELITES_SAMPLER_SEED and the persistent per-island job ordinal make each selection restart-stable. MAPELITES_SAMPLER_RECIPE_COOLDOWN_JOBS excludes that many recent unordered (base, inspirations) recipes, and MAPELITES_SAMPLER_MAX_RESAMPLE_ATTEMPTS bounds the search for a different recipe before an unavoidable reuse is recorded. MAPELITES_SEED_POPULATION_SIZE sets the initial seed population size per island.
    • Map-Elites embedding cache: repo-state embeddings always use the Postgres-backed file cache and persist commit aggregates to support incremental-only ingestion.
    • Map-Elites experiment root commit: MAPELITES_EXPERIMENT_ROOT_COMMIT pins the logical root commit for repo-state bootstrap and incremental-only ingestion. The scheduler resolves the value to a canonical full hash and uses it for startup approval scans and pinned ignore rules. Experiment identity is provided explicitly via EXPERIMENT_ID (not derived from the root commit). At scheduler startup, Loreley pins repository-root ignore rules used by repo-state embeddings by reading .gitignore + .loreleyignore from the root commit and storing the combined ignore text in memory for the lifetime of the scheduler process.
    • database_dsn: computed property that returns a SQLAlchemy-compatible DSN, preferring DATABASE_URL when set and otherwise building one from the individual DB fields (with credentials URL-encoded).
    • export_safe(): helper that returns a dict of non-sensitive configuration values suitable for logging.
    • effective_fingerprint(): helper that returns a SHA-256 fingerprint of the masked effective settings export for result provenance.

    Access helpers¶

    • get_settings(): cached factory that instantiates Settings, logs a concise summary of the environment and DB host using rich/loguru, and returns a singleton instance for reuse across Loreley.

    CLI¶

    • loreley config dump: dumps the effective configuration as JSON or YAML, with credentials masked by default. Useful for troubleshooting and reproducibility.
